# PO → GRN: confirmed behaviour

**Confirmed by the user on 2026-09-24.** Built the same way as Indent → PO (its reference flow):
ERP APIs only, runs outside the job engine, ERP bookkeeping is what prevents duplicates.

| Question | Decision |
|---|---|
| Which POs | **Authorised POs only** (`POHAUTHBY` set) — every eligible one, not only POs the agent created |
| Trigger | Sweep all eligible authorised POs, shaped like Indent → PO (discover → convert each) |
| Received quantity | The line's **pending** quantity (PO qty − received − short-closed), in PUOM and IUOM. No over-receipt tolerance |
| Invoice No | One value a user types once on the automation screen, stored in the flow's settings, stamped on **every** GRN the agent creates, editable at any time (confirmed 2026-09-24) |
| Invoice Date | **The day before** the GRN date |
| GRN date | Today; must be ≥ PO date and within the site's finance period |
| Warehouse | The PO line's own warehouse |
| GRN authorisation | **Left to a person.** The agent never calls `inventory/grn/authorizegrn` |
| "Parameter" items | An item needing batch, heat, inward, serial, mfg-batch **or a shelf-life expiry date**, or an **LBT (sized) line**, is never received by the agent |
| Blanket POs | Skipped — no fixed quantity to receive (confirmed 2026-09-24) |
| History | Saved to the automation database: `PoGrnRun` + `PoGrnReceipt` (confirmed 2026-09-24) |
| Receipt mode (a setting on the screen) | **Complete** — receive a PO only if *every* pending line is parameter-free, else skip the whole PO. **Partial** — receive every PO with at least one parameter-free line, GRN only those lines, leave the rest pending for a person (confirmed 2026-09-24) |
| Settings / screen | Its **own** settings, table and agent API — shares nothing with Indent → PO's config or endpoints — shown as a separate section on the **same** automation dashboard (master toggle, Run, Schedule Time, like Indent → PO) |
| Scope | Regular (`GR/OR`) and Capital (`GR/CG`) material POs |

## Facts from the ERP code that the design depends on

- Discovery: `POST Purchase/POEntry/List/{locIds}/{companyId}/{locationId}?Status=A` (`CSP_XPOHEADLIST_EM`)
  returns authorised POs; its `isgrn` column is 1 when a line still has quantity pending.
- Lines + tax rows: `GET inventory/grn/getposearchdetails/{site}/{wh}/{vendor}/{poAutoId}/DIS/{cur}/{type}/{date}`
  (`CSP_XPOHead_GetPOSearch`, mode `DIS`). Each line already carries the item-master flags
  `mimbchreqd`, `miminwdreq`, `mimheatreq`, `mimitmsrreqd`, `mimmfgreq` (from `MITMMAST`), so the skip rule
  needs no extra call.
- Create: `POST inventory/grn/create` (`GRNDataModel`). The number comes back only in `message`:
  `GRNCreated#FY/grp/site/no#autoId`; `data` is empty.
- **The PO's received quantity is updated only when tax rows are posted** (`insertRateStructureDetail`
  calls `CSP_XGRNDTL_UpdatePOQTY` only if `updatecount > 0`). A GRN sent without `rateStructureDetail`
  leaves the PO looking unreceived, and the next sweep would receive it again.
- `CSP_XGRNDTL_UPDATEPOQTY` refuses over-receipt ("GRN QTY Can not Be greter then Po QTY").
- Nothing in the ERP stores batch/heat/serial/mfg-batch numbers before receipt (not on `XPOITMDTL`, not
  on gate inward). Only the **inward number** can be generated by the ERP — when Inventory Policy
  `isinwardAutoGen` is on and the item does not also need heat (`inventory/grn/getmaxParamValue`).

**Why:** these decide which POs the agent may touch and what it types into fields a storekeeper normally fills.

**How to apply:** don't add an authorise step and don't relax the skip rule without a new confirmation
here. Scope confirmed 2026-09-24: backend only for now — two APIs (settings, trigger), inbound API
key only; no WebApp2 work yet. Implementation: [docs/flows/po-to-grn/README.md](../../docs/flows/po-to-grn/README.md). Related: [autoshop-chain-ownership.md](autoshop-chain-ownership.md) (same "agent's scope" principle).
